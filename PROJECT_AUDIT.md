# KampusPulse — Project Audit

## ⚠️⚠️⚠️ THE most critical finding of the entire audit (2026-07-19): unauthenticated free-money mint

While building integration tests for the money-flow bug below, testing turned up something worse. **`increment_wallet_balance`/`decrement_wallet_balance`/`decrement_product_stock` are `SECURITY DEFINER` Postgres functions with no caller-identity check inside their body at all.** PostgreSQL grants `EXECUTE` on newly created functions to `PUBLIC` by default, and nothing in any of the 30 original migrations ever revoked that.

**Practical impact:** a fully **unauthenticated** request — no login, no account, nothing but the app's own public `NEXT_PUBLIC_SUPABASE_ANON_KEY` (which every Next.js app ships client-side, visible to anyone via browser devtools or reading the bundled JS) — could call `POST /rest/v1/rpc/increment_wallet_balance` with an arbitrary `p_user_id` and `p_amount` and mint unlimited money into any wallet. **Confirmed empirically, not theoretically**: against a local Supabase instance, a plain unauthenticated `curl` request credited a test wallet with ₵999,999. `decrement_wallet_balance` (silently zero out anyone's balance) and `decrement_product_stock` (arbitrarily deplete or manipulate any seller's stock) had the identical gap.

**Fix applied** (migration `033_fix_rpc_privilege_escalation.sql`): the two wallet functions now check `auth.role() <> 'service_role' AND p_user_id IS DISTINCT FROM get_profile_id()` and raise an exception — the service role (webhook/admin credits) still bypasses, but any end-user call is restricted to their own wallet. `decrement_product_stock` has no equivalent clean per-call ownership check available (the caller is the buyer, not the product's owner), so as a partial mitigation its `EXECUTE` grant was revoked from `PUBLIC` entirely and re-granted only to `authenticated`/`service_role` — blocks the highest-severity unauthenticated case; a fully complete fix would need to validate an order context and is tracked as a follow-up.

**Verified exhaustively**, not just the happy path: unauthenticated attack → blocked; authenticated user targeting *someone else's* wallet → blocked; authenticated user crediting/debiting *their own* wallet → still works; service-role (webhook/admin) crediting any wallet → still works. All 4 scenarios are now permanent regression tests in `tests/integration/wallet-rpc-security.test.ts`.

## ⚠️⚠️ Also critical: 8 of 9 `FOR ALL` RLS policies schema-wide were missing `WITH CHECK`, and RLS was never enabled at all on 6 tables

While verifying the fix above, a **third** class of bug turned up, and it's schema-wide, not a one-off. Two separate, compounding mistakes:

1. **Missing `WITH CHECK`.** A `CREATE POLICY ... FOR ALL USING (expr)` with no explicit `WITH CHECK` does **not** implicitly reuse the `USING` expression the way policy comments elsewhere in this codebase assumed — confirmed empirically (the one policy that always had an explicit `WITH CHECK`, `wishlists_own`, behaved correctly the whole time; the 8 that didn't, didn't). Affected: `admin_logs_admin_all`, `fcm_tokens_all`, `notification_broadcasts_admin_all`, `notifications_all`, `platform_settings_admin_write`, `"Admins can manage products"`, `promotions_admin_all`, `refunds_admin_all`. Fixed in migration `034_fix_missing_with_check_policies.sql` — each got an explicit `WITH CHECK` copied verbatim from its own `USING` clause.
2. **RLS never enabled at all**, on top of that, for 6 tables: `admin_logs`, `audit_logs`, `platform_settings`, `refunds`, `user_presence`, `typing_indicators` (`categories` is a 7th table with RLS off, but that one's intentional — public reference data). `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` was simply never called for these in any migration, meaning **every policy on them, fixed or not, was completely inert** — this is what fix #1 above was actually hiding: even after adding the correct `WITH CHECK` to `platform_settings_admin_write`, a non-admin could *still* overwrite platform-wide settings via an upsert, because RLS enforcement itself was off for the whole table. `migration 017`'s own comment claims "platform_settings has RLS enabled with zero policies" — that premise was false from the start. Fixed in migration `035_enable_missing_rls.sql`.

**Worst-case practical impact**, pre-fix: `audit_logs` (old/new data dumps of every sensitive row change app-wide, plus actor IDs and IP addresses) and `admin_logs` (the admin action audit trail) were both fully readable *and* writable/forgeable by any direct request against Supabase's REST API, entirely bypassing the app. `refunds` (financial records) and `platform_settings` (maintenance mode, rider auto-assign, etc.) had the same exposure.

**Verified**: every one of the 9 tables now correctly blocks a non-admin/non-owner and correctly allows the legitimate owner/admin — locked in as permanent regression tests across `tests/integration/rbac.test.ts` and `tests/integration/admin-only-tables-rls.test.ts`.

**A note on the local test environment itself**, since it took real effort to untangle from the app bugs above: `supabase db reset` (as opposed to a fresh `supabase start`) does **not** replay the one-time container-init grants a real hosted Supabase project gets automatically — every table ends up with zero default privileges for any role, including `service_role`. This is a CLI/Docker quirk of local testing, not a product bug, and is NOT what caused any of the findings above (those were all confirmed via `has_function_privilege`/`has_table_privilege`/`pg_policy` queries and direct exploit attempts, independent of this). A new script, `scripts/local-db-grants.sh`, applies the missing baseline grants for local dev/CI; it deliberately does **not** touch function-level grants, so it can never accidentally undo migration 033's fix.

## ⚠️ Critical finding discovered during Phase 3 (2026-07-19)

**`middleware.ts` was never actually running.** This project's App Router code lives entirely under `src/app/`, but `middleware.ts` sat at the project root. Next.js requires middleware to live *inside* `src/` when a `src` directory is used for the app — at the root, it is silently never detected, in both `next dev` and `next build` (confirmed empirically: `.next/server/middleware-manifest.json` had `"middleware": {}` even for a trivial one-line middleware file, in every Next.js version tested, including the original pre-upgrade 15.0.5 code before any changes this session).

**Practical impact:** every page-level protection described in this file and in the original codebase comments — bouncing unauthenticated users off private routes, redirecting non-admins away from `/admin`, redirecting non-riders away from `/rider`, and bouncing suspended/banned users off private pages — has never actually executed, for as long as the file was misplaced (not determined how long; not a regression introduced this session). This was **not** caught earlier because the defense-in-depth API-level checks (`requireProfile`/`requireRole` in route handlers) and Postgres RLS independently gate actual data access — so this was a real gap in page-level UX/redirect protection, not necessarily a data-exfiltration hole, but a serious one: an unauthenticated browser could load the HTML shell of any "private" page, and a banned user's browser was never redirected away from pages it could still (mostly) not fetch data into.

**Fix applied:** moved the file to `src/middleware.ts` (`git mv` — full history preserved). Verified via `.next/server/middleware-manifest.json` now showing a populated entry, "ƒ Middleware" appearing in the `next build` route summary, and a live `next dev` request to `/login` correctly returning a `Content-Security-Policy` header (see H3 below) — which only happens if middleware executes. **Strongly recommend the user independently verify this in their real deployment** (e.g. Vercel) since this session's environment has no real Supabase credentials to fully exercise the redirect logic end-to-end.

## ⚠️⚠️ Even more critical finding (2026-07-19, found during Medium-item work): real Paystack payments never actually completed

**`transactions` has had Row Level Security enabled since migration 009 with only a SELECT policy — no INSERT policy has ever existed, in any of the 30 original migrations.** Every payment code path (`PaymentService.initializePayment` for real Paystack payments, `settleConfirmedPayment` shared by dev-mode and wallet payments) inserts into `transactions` using the RLS-bound anon-key client, and the app code never checks that insert's error. This insert has been **silently rejected by Postgres RLS this entire time.**

**Practical impact — this is the single most severe finding of the whole audit:** for a *real* Paystack payment (actual mobile money/card, not wallet balance, not dev mode), no pending `transactions` row is ever created. When Paystack's `charge.success` webhook later fires, its idempotency guard (`UPDATE transactions SET status='success' WHERE reference=X AND status != 'success'`) finds **zero matching rows** — because the row was never inserted, not because it's a duplicate delivery — and the webhook's own logic treats this as `{duplicate: true}` and **skips every fulfillment side effect**: order confirmation, stock decrement, delivery dispatch, buyer/seller notifications, task escrow flip, ride payment marking, and wallet top-up credit. **A student could pay real money via Paystack and their order/task/ride would never be marked paid.** Dev-mode and wallet payments still mostly "work" despite hitting the same broken insert, because their fulfillment logic runs inline in the same function call rather than depending on the transaction row existing — they just silently lose their transaction-history/audit-trail entry (which also explains why admin revenue metrics, which sum from `transactions`, would under-report).

**Verified empirically, not just by reading the code:** spun up a local Supabase instance via Docker, applied all 30 migrations, created a real authenticated test user, and attempted the exact insert the app performs — got back `"new row violates row-level security policy for table \"transactions\""` (HTTP 403). Applied the fix, retried, got HTTP 201. Also confirmed the fix's ownership check (`get_profile_id() = user_id`) correctly still rejects inserting a transaction against a different user's profile — no new IDOR was introduced.

**Fix applied:** new migration `031_fix_transactions_insert_rls.sql` adds `CREATE POLICY "transactions_insert" ON public.transactions FOR INSERT WITH CHECK (get_profile_id() = user_id);`. `full_setup.sql` regenerated to include it. **This migration must be run against the live Supabase database immediately — this is the highest-priority action item in this entire audit.**

## Phase 1 Report

### 1. What the project is
KampusPulse is a campus "super-app" built for students at the University of Cape Coast (UCC), Ghana. It bundles four modules under one Next.js application:
- **EDWOM** — peer-to-peer/vendor student marketplace (buy/sell used goods, food, etc.)
- **Y3 ADWUMA** — a task/gig board (post a task, apply, escrow payment, release on completion)
- **EZZYRIDE** — campus ride-hailing and package/food delivery with live rider tracking
- **Messages / Notifications / Wallet** — cross-cutting real-time chat, push notifications, and an in-app wallet used to pay across all three modules

Payments are done via Paystack (Ghanaian mobile money: MTN MoMo, Telecel Cash, AirtelTigo, plus card), with a "dev payment" fallback mode when Paystack isn't configured. It is a monolithic Next.js 15 App Router project backed by Supabase (Postgres + Auth + Storage + Realtime), intended to deploy to Vercel.

### 2. Current architecture
- **Framework**: Next.js 15 (App Router), single deployable app — no separate backend service.
- **API layer**: Next.js Route Handlers under `src/app/api/**` (56 route files) act as a thin BFF: they call `requireAuth`/`requireProfile`/`requireRole` for authn/authz, `validateCsrf` for state-changing requests, Zod validators for input shape, then a **service** (`src/lib/services/*`) which encapsulates business logic, which in turn calls a **repository** (`src/lib/repositories/*`) that wraps Supabase queries.
- **Data layer**: Supabase Postgres with Row Level Security (RLS) as the second line of defense behind the API layer (`supabase/migrations/009_rls_policies.sql` and later fix migrations 013–029).
- **Auth**: Supabase Auth (email+password) via `@supabase/ssr`, session carried in cookies, enforced in three places: `middleware.ts` (page-level redirects), `requireProfile()`/`requireRole()` (API-level), and Postgres RLS (data-level).
- **Realtime**: Supabase Realtime channels for chat/notifications/ride tracking (`supabase/enable_realtime.sql`).
- **Client state**: React Context (`auth-context.tsx`, `notifications-context.tsx`) + a couple of small hooks (`useCart`, `useWishlist`) backed by API calls rather than a global store (zustand is installed but unused — see §16).
- **Maps**: Leaflet + OpenStreetMap (free, no API key) — the component is still named `GoogleMap.tsx` for historical reasons (see its own header comment) after commit `ff788ea` replaced the actual Google Maps implementation.
- Overall this is a fairly conventional 3-tier layered architecture (route → service → repository → Supabase), which is more disciplined than most single-dev Next.js/Supabase projects reach.

### 6. Database structure
Schema is defined incrementally across `supabase/migrations/001`–`029` (extensions/profiles → stores/categories/products → orders/cart → tasks → rides/deliveries → chat → payments/wallets → notifications/audit → storage buckets → RLS → functions/triggers → then 18 further fix/feature migrations). Core tables:
- `profiles` (role: student/vendor/rider/admin; status: active/suspended/pending/banned) — extends `auth.users`
- `stores`, `categories`, `products` (full-text search via `pg_trgm`)
- `orders`, `order_items`, `cart_items`
- `tasks`, `task_applications`
- `rides`, `deliveries`, `rider_profiles` (verification + live lat/lng)
- `chat_rooms`, `messages`
- `reviews` (cross-module ratings)
- `wallets`, `transactions`, `refunds`
- `notifications`, `notification_preferences`
- `admin_logs`, `platform_settings`, `promotions`
RLS is enabled on all sensitive tables via `get_profile_id()` (maps `auth.uid()` → profile id) helper policies. **Important structural issue**: alongside the 29 numbered migrations there is a second, parallel schema definition — `supabase/schema.sql` and `supabase/full_setup.sql` — plus five standalone `supabase/fix_*.sql` scripts, presented in the onboarding script (`scripts/supabase-setup.sh`) as *the* thing to run in a fresh project. These have drifted from the migrations: e.g. `full_setup.sql` line 17 defines `role IN ('student','rider','admin')` (no `'vendor'`), while `supabase/migrations/001_extensions_and_profiles.sql` line 17 defines `role IN ('student','vendor','rider','admin')`. A fresh Supabase project set up per the README/scripts would get a **different, out-of-date schema** than what the 029 migrations actually produce. No single source of truth for the schema (§17/§23).

### 7. API endpoints
56 route files under `src/app/api/`, grouped as: `auth/*` (login, register, resend-confirmation, reset-password), `profile`, `products[/[id]]`, `cart`, `orders[/[id]]`, `wishlist`, `tasks[/[id]/{apply,accept,reject,pay}]`, `rides[/[id]/{claim,pay}]`, `deliveries[/[id]/claim]`, `rider/{availability,location}`, `messages/{rooms,[roomId]}`, `notifications`, `promotions/validate`, `wallet/topup`, `paystack/{initialize,verify,refund,webhook}`, `fcm/register`, `upload`, `csrf`, and a full `admin/*` set (analytics, logs, metrics, notifications, orders, payments, products, promotions, reviews, riders, settings, users). A partial OpenAPI 3.0.3 spec exists at `docs/openapi.yaml` (covers products endpoints in the excerpt reviewed; not verified to cover all 56 routes).

### 8. Authentication flow
Email+password via Supabase Auth. Login and registration are proxied through this app's own `/api/auth/login` and `/api/auth/register` routes (not called directly from the browser) specifically so they can be rate-limited (`rateLimit(ip:email, "auth")`, 30/min) — the code's own comments explain this was previously a gap (unlimited password-guessing was possible when the browser called Supabase directly). Session is stored in cookies via `@supabase/ssr`; `middleware.ts` reads the session on every request, redirects unauthenticated users away from `PRIVATE_ROUTES` and authenticated users away from `AUTH_ROUTES` (with a carve-out for password-recovery links), and additionally blocks `suspended`/`banned` profiles from private pages. Email confirmation and password reset are handled via `/api/auth/resend-confirmation` and `/api/auth/reset-password` + `/auth/callback`. OAuth scaffolding exists (`src/lib/auth-oauth.ts`) but wasn't confirmed wired into a login UI in this pass.

### 9. User roles
Four roles enforced via a Postgres CHECK constraint on `profiles.role`: `student` (default), `vendor` (marketplace sellers — note: absent from `full_setup.sql`, see §6), `rider` (EZZYRIDE/delivery drivers, has a linked `rider_profiles` row for verification/location), `admin` (full dashboard access). A separate `status` field (`active`/`pending`/`suspended`/`banned`) gates access independently of role — enforced in `middleware.ts` (page redirect) and `requireProfile()` (API-level, `src/lib/middleware/auth.ts:32-40`), per the code comment, "was written but never checked" until a recent fix (commit `dee40a8`).

### 11. Design patterns used
- **Layered architecture** (route handler → service → repository → Supabase client), applied fairly consistently across ~50 of the 56 API routes.
- **Repository pattern** isolating Supabase query shape from business logic.
- **Middleware/decorator-style cross-cutting concerns** (`requireAuth`/`requireProfile`/`requireRole`, `validateCsrf`, `rateLimit`) called explicitly at the top of each handler (not real middleware chaining — each route opts in manually, which is also a consistency risk, see §20).
- **Centralized error handling**: `AppError` class + `handleApiError()` maps typed errors to HTTP responses uniformly.
- **Defense in depth**: the same authorization rule is often enforced at two or three layers (UI, `middleware.ts`, API, RLS) — visible in `messages/[roomId]/route.ts` (checks `participants.includes(profile.id)` in addition to relying on RLS) and `deliveries/[id]/route.ts` (explicit comment noting it *relies* on RLS scoping).
- **Idempotency by design**: the Paystack webhook (`src/app/api/paystack/webhook/route.ts:53-62`) guards side effects behind a conditional `UPDATE ... WHERE status != 'success'` so retried webhook deliveries can't double-credit wallets or double-fulfill orders.
- **Client-content sniffing over trust-the-header** for uploads (`src/lib/services/upload.service.ts:18-46`) — validates real file bytes, not just the client-asserted MIME type.

### 19. Performance bottlenecks
- `src/app/api/admin/metrics/route.ts` fires 17 separate Supabase queries via `Promise.all` on every dashboard load, several of them full-table `count: 'exact'` scans (`profiles`, `products`, `orders`, `tasks`, `rides`) with no caching layer — will degrade linearly as tables grow; there's no memoization/cache (e.g. Redis, which is already a dependency for rate limiting) for this admin-only but potentially frequently-polled endpoint.
- `product.repository.ts` and `task.repository.ts` search use `ilike '%term%'` (leading wildcard), which cannot use a standard btree or even the `pg_trgm` GIN index efficiently for prefix-agnostic search at scale — fine at current data volumes, will become a bottleneck as `products`/`tasks` grow into the tens of thousands of rows.
- `reactStrictMode: false` in `next.config.ts:4` — disabling Strict Mode removes a development safety net for detecting unsafe side effects/double-invocation bugs; it doesn't affect production performance directly but suggests some effects/subscriptions (e.g. the realtime chat/notification listeners) may not be safely re-entrant, which could manifest as duplicate subscriptions or listener leaks in production.
- No visible pagination limit ceiling enforced in some list endpoints beyond Zod defaults — worth confirming `limit` params are capped server-side everywhere (spot-checked `products`/`tasks`, which do use `.range()` with a bounded `limit`, but not exhaustively checked across all 56 routes).

### 20. Security issues
Overall this codebase shows above-average security awareness for its category (constant-time comparisons, CSRF tokens, MIME sniffing, RLS-as-defense-in-depth, idempotent webhooks are all present and explained in code comments). The issues below are the concrete, specific gaps found:

1. **Vulnerable Next.js version — CVE-2025-29927 (middleware authorization bypass)**. `package.json:48` pins `"next": "^15.0.5"` and `package-lock.json` resolves the installed version as exactly **15.0.5** (confirmed via `node_modules/next` lockfile entry). Next.js versions before 15.2.3 are vulnerable to an authorization bypass where a crafted `x-middleware-subrequest` header causes `middleware.ts` to be skipped entirely. Since this app's page-level auth gating, admin/rider route protection, and suspended/banned enforcement all live in `middleware.ts` (`middleware.ts:14-104`), this is a direct path to bypassing those page-level checks. Impact is partially mitigated because several (not all — see #3 below) API routes independently enforce auth via `requireProfile`/`requireRole`, but this is still a critical, fully-patchable finding (upgrade to Next.js ≥15.2.3).

2. **Unauthenticated live location/PII disclosure**. `src/app/api/rides/online-count/route.ts` has no authentication check at all, and `rider_profiles_select` RLS policy (`supabase/migrations/009_rls_policies.sql:127`) is `USING (true)` — public, unrestricted read. Together, any unauthenticated visitor can call this endpoint and receive the live `lat`/`lng`, name, avatar, and rating of every currently-online rider. This is a location-privacy exposure (stalking/tracking risk for riders) with no auth, no rate limit, and no obfuscation.

3. **Inconsistent authorization enforcement — `/api/profile` bypasses the ban/suspend check**. `src/lib/middleware/auth.ts:32-40` centralizes the "block suspended/banned accounts" rule inside `requireProfile()`. But `src/app/api/profile/route.ts:4-14` (GET) and `:29-33` (PATCH) hand-roll their own `supabase.auth.getUser()` check instead of calling `requireProfile()`, so a suspended or banned user can still read and **update** their own profile via direct API call even though the UI/middleware would otherwise redirect them. Same pattern in `src/app/api/admin/metrics/route.ts:4-19` and `src/app/api/rides/online-count/route.ts` (the latter has no auth at all, see #2) — three routes reimplement auth instead of reusing the shared, audited helper, so fixes to the central policy (like the recent ban-enforcement fix) don't automatically propagate to them.

4. **PostgREST filter-string injection via unescaped search input**. `src/lib/repositories/product.repository.ts:54` and `src/lib/repositories/task.repository.ts:22` build the `.or()` filter argument by directly interpolating the user-supplied `search` query parameter into a PostgREST filter-syntax string: `` `title.ilike.%${params.search}%,description.ilike.%${params.search}%` ``. Because PostgREST's filter DSL treats commas, periods, and operator names as syntax, a search string containing those characters (e.g. `x%,id.neq.<something>` or values that inject extra `.or()`/`.and()` clauses) is not classic SQL injection but is a **filter/query injection** — it lets a caller manipulate which logical conditions are ANDed/ORed into the query in ways the developer didn't intend, potentially exposing rows that should be filtered out (e.g. combined with the `tasks_select`/`products_select` "public" RLS policies at migration `009_rls_policies.sql:44,87`). No escaping or use of Supabase's structured `.or()` parameter object is present. This should be re-validated with adversarial input and fixed by escaping commas/parens or switching to parameterized `.textSearch()`/multiple chained `.ilike()` calls.

5. **Payment/wallet endpoints lack rate limiting.** `rateLimit()` (`src/lib/middleware/rate-limit.ts`) is only invoked from `auth/login`, `auth/register`, `auth/resend-confirmation`, `auth/reset-password`, `products`, and `tasks` (confirmed via repo-wide grep — 6 of 56 routes). `paystack/initialize`, `paystack/verify`, `wallet/topup`, `tasks/[id]/pay`, `rides/[id]/pay`, and `upload` have no rate limiting, leaving them open to abuse (e.g. hammering Paystack's API via `paystack/initialize`, or repeated large-file upload spam against `upload/route.ts`).

6. **Weak password policy.** `src/app/api/auth/register/route.ts:9` only requires `z.string().min(6)` — no complexity, common-password, or breach-list check. Combined with rate limiting at 30/min (not particularly strict), brute-forcing weak passwords is more feasible than it should be.

7. **CSP allows `'unsafe-inline'` and `'unsafe-eval'` for scripts.** `next.config.ts:24` sets `script-src 'self' 'unsafe-inline' 'unsafe-eval' https://js.paystack.co`. This significantly weakens the CSP's XSS mitigation value — any injected inline script or `eval`-based payload would execute despite the CSP header being present. Given `sanitizeText()` (`src/lib/middleware/sanitize.ts`) is a hand-rolled regex-based HTML stripper (not a real HTML sanitizer library like DOMPurify) used ahead of storing user text (chat messages, reviews, etc.), a bypass of that regex combined with `unsafe-inline` would achieve stored XSS with no CSP backstop. The regex approach itself is fragile — regex-based tag stripping is well known to be bypassable via malformed/nested tags, encoded attributes, or non-`<script>` event handlers that don't match `on\w+=` exactly (e.g. handlers split across tags, or unusual whitespace).

8. **Service-role (admin) Supabase client used inside a webhook driven entirely by external, attacker-influenceable event data.** `src/app/api/paystack/webhook/route.ts:30-33` creates an admin (service-role, RLS-bypassing) client and then trusts `metadata.order_id`/`order_ids`/`task_id`/`ride_id`/`user_id` from the Paystack event payload to decide which rows to update (`:64-121`). This is safe *only* insofar as the HMAC signature check (`:10-27`, correctly constant-time) guarantees the payload truly came from Paystack — which it does — but it means the entire trust boundary for wallet credits/order fulfillment rests on that one signature check plus `PAYSTACK_WEBHOOK_SECRET` never leaking. Worth confirming `PAYSTACK_WEBHOOK_SECRET` is never logged (spot check didn't find it logged) and that Paystack's IP allowlisting or an additional secret-path convention is also considered as defense in depth.

9. **No CORS configuration found for API routes** — Next.js route handlers on the same origin don't strictly need one, but there's no explicit `Access-Control-Allow-Origin` handling anywhere (`vercel.json`, `next.config.ts`, or route handlers), meaning if any route is ever intended to be called cross-origin (e.g. a future mobile app), the default same-origin-only behavior may silently break it, or someone may be tempted to add a permissive `*` CORS header later without realizing the security implications for the cookie-authenticated API.

10. **No secrets found hard-coded in source** (grep for `sk_live_`, `AIza...`, private-key blocks, service-role JWT patterns across `src/` and `supabase/` came back clean) — `.env.local.example` correctly uses placeholder values only. This is a positive finding, not a gap.

### 21. Code quality issues
- **Hand-maintained, partially-`any`-typed database types.** `src/types/database.ts:9-11` explicitly types `TableInsert<T>`/`TableUpdate<T>` as `any` (with `eslint-disable-next-line @typescript-eslint/no-explicit-any`) rather than generating types from the live schema via the Supabase CLI. This is likely why the codebase is peppered with `as never`/type-assertion casts around `.update()`/`.insert()` calls (e.g. `src/contexts/auth-context.tsx:111`, `src/app/api/messages/[roomId]/route.ts:42,85,93`) — the type system isn't actually catching schema/shape mismatches on writes, which somewhat defeats the purpose of `strict: true` in `tsconfig.json`.
- **`eslint.ignoreDuringBuilds: true`** in `next.config.ts:5` — lint errors cannot fail a production build (though CI does run `npm run lint` as a separate step, so this mainly matters for local/direct `next build` runs bypassing CI).
- **26 `console.log`/`console.error`/`console.warn` calls** left in `src/` — acceptable for server-side error logging in a few places (e.g. webhook handlers), but not centralized through any structured logger, so there's no way to distinguish "expected best-effort failure" logs from real incidents in production log aggregation.
- **Inconsistent authorization plumbing** — see §17/§20 item 3: three routes bypass the shared `requireAuth`/`requireProfile`/`requireRole` helpers and hand-roll equivalent (but not centrally-fixable) logic.
- **Thin/low-value test coverage** — `tests/auth/rbac.test.ts` tests hardcoded local arrays, not actual route or RLS behavior (§14); only 6 spec files total (`tests/api/payment.test.ts`, `tests/auth/rbac.test.ts`, `tests/unit/{app-error,checkout.service,fare.service,sanitize,task-lifecycle,validators}.test.ts`) for a codebase with 56 API routes and 8 service classes — most services/routes have no direct test coverage.
- **Stale/misleading README** — describes the map feature as "Simulated Google Maps view with live rider dots" (README.md:87) when the app now uses real Leaflet/OpenStreetMap; the "Pages Summary" table's "✅ 200" status column reads as manually-asserted rather than verified, and the environment variable list omits `PAYSTACK_WEBHOOK_SECRET`, all Firebase vars, and `UPSTASH_REDIS_REST_*` that `.env.local.example` actually defines.

### 22. Scalability concerns
- Admin metrics endpoint's 17-query fan-out with full-table counts (§19) will slow proportionally to data growth with no caching.
- Rate limiting silently degrades to a per-instance **in-memory Map** (`src/lib/middleware/rate-limit.ts:21-33`) whenever Upstash Redis env vars aren't configured. In a multi-instance serverless deployment (Vercel), this in-memory fallback provides **no real protection at all** — each function instance has its own counter, so the effective rate limit is `limit × number of concurrently warm instances`, not the configured limit. This should be flagged clearly as "dev-only fallback, not production-safe" if it isn't already understood as such.
- Leading-wildcard `ilike` search (§19) doesn't scale past medium data volumes without a proper full-text-search index (`pg_trgm` is installed per `supabase/schema.sql:6` but the queries don't appear to use trigram-optimized operators like `%` similarity or `to_tsvector`/`websearch_to_tsquery`).
- Realtime chat/notifications rely on Supabase Realtime channels; no evidence of connection/subscription cleanup issues was specifically traced, but `reactStrictMode: false` (§19) makes it harder to catch double-subscription bugs before they reach production at scale.
- Single Postgres database serving marketplace, tasks, rides, chat, and payments together — reasonable at current scale, but ride/delivery location writes (`rider/location` polling) and chat could become hot paths competing with transactional order/payment writes on the same database as usage grows; no read-replica or separate hot-path store is in place (Redis is only used for rate limiting, not for ephemeral rider location).

### 23. Technical debt
- **Two parallel, drifted schema sources** (`supabase/migrations/*` vs. `supabase/schema.sql`/`full_setup.sql`/loose `fix_*.sql` scripts) — highest-priority structural debt; a new environment set up via the documented path (`scripts/supabase-setup.sh` → `full_setup.sql`) will not match production if production was built up via the numbered migrations (§6/§17).
- **Unused dependencies** inflating install size and audit surface: `zustand`, `msw`, `@testing-library/react`, `@googlemaps/js-api-loader`, `@types/google.maps`, and `vercel` as a `devDependency` (§16).
- **Auth/authorization logic duplicated in 3+ places** instead of centralized (§17/§20/§21) — a maintenance and security-drift risk: the next ban-enforcement-style fix might again miss routes that don't go through the shared helpers.
- **Rate limiting rolled out to only 6 of 56 routes**, and its production-safety depends on optional Redis configuration with a silent, non-equivalent in-memory fallback (§22).
- **Hand-maintained DB types with `any` Insert/Update** instead of CLI-generated types — ongoing risk of silent schema/type drift (§21).
- **Low test coverage relative to surface area** (56 routes, 8 services, 7 repositories vs. 6 spec files, one of which doesn't test real code) — refactoring or Phase 2+ changes will have little regression safety net.
- **README drift** from actual implementation (Google Maps → Leaflet, incomplete env var documentation) — onboarding friction for new contributors.
- **Vulnerable pinned framework version** (Next.js 15.0.5, CVE-2025-29927) is itself a debt item requiring a dependency bump plus regression testing of `middleware.ts` behavior post-upgrade.
